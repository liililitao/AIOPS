## 3. Agent 图编排 (LangGraph)

### 3.1 State 定义 (PlanExecuteState)

整个图里 5 个节点不直接通信，而是通过 `PlanExecuteState` 字典交换数据：

```
                         PlanExecuteState
┌────────────────────────────────────────────────────────────────┐
│  input:          str             用户原始输入 (不变)             │
│  selected_skill: str             SkillRouter 选中的 skill 名     │
│  skill_reason:   str             为什么选它 (可观测)             │
│  plan:           List[str]       待执行步骤列表                  │
│  past_steps:     List[(step,result)]  已完成的步骤 (operator.add)│
│  response:       str             最终报告 (非空 → END)           │
│  iteration:      int             当前步数 (防死循环)             │
│                                                                    │
│  ── Reroute 相关 (Supervisor + Handoff 模式) ──                  │
│  pending_reroute: bool           Replanner 提议切 Skill          │
│  reroute_count:  int             已 reroute 次数                 │
│  tried_skills:   List[TriedSkill] 黑名单 (operator.add)          │
│  inside_fork:    bool            是否在 fork 子图内              │
│                                                                    │
│  ── 可观测性 ──                                                   │
│  transition_history: List[StateTransition] (operator.add)        │
│  permission_mode: str            工具权限模式                    │
└────────────────────────────────────────────────────────────────┘
```

State 更新规则:
- 普通字段 = **覆盖**（新值替换旧值）, 如 `input`, `plan`, `response`
- `Annotated[List, operator.add]` = **追加**（新值拼到旧值后面）, 如 `past_steps`, `transition_history`

### 3.3 两条条件边的路由逻辑

**条件边 #1：`route_after_skill` — SkillRouter 之后去哪？**

```python
def route_after_skill(state):
    # 优先级 1: Router 已给 response (非运维输入) → END
    if state["response"]:         return END

    # 优先级 2: 已在内嵌子图 (防无限递归 fork)
    if state.get("inside_fork"):  return "planner"

    # 优先级 3: Skill 标记 context=fork → fork_skill 子图
    if skill.context == "fork":   return "fork_skill"

    # 优先级 4: 默认 → 标准 Plan-Execute-Replan
    return "planner"
```

**条件边 #2：`should_end` — Replanner 之后去哪？**

```python
def should_end(state):
    # 优先级 1: 报告已生成 → END
    if state["response"]:         return END

    # 优先级 2: 切 Skill → 回到 Planner 重新规划
    if state.get("pending_reroute"): return "planner"

    # 优先级 3: plan 空且无 response → 强制终止
    if not state["plan"]:         return END

    # 优先级 4: 继续 → Executor 下一步
    return "executor"
```

### 3.4 每个节点对 State 的读写

| 节点 | 读取 | 写入 | 执行次数 |
|------|------|------|----------|
| **skill_router** | `input` | `selected_skill`, `skill_reason`, (`response`) | 1 次 |
| **planner** | `input`, `selected_skill` | `plan`, `iteration=0` | 1 次 (或 reroute 时多次) |
| **executor** | `plan[0]`, `iteration`, `selected_skill` | `past_steps` (追加), `iteration+1` | N 次 |
| **replanner** | `input`, `plan`, `past_steps`, `iteration`, `selected_skill` | `response` 或 `plan` 或 `pending_reroute` | N 次 |
| **fork_skill** | `input`, `selected_skill` | `response` | 0-1 次 |

### 3.5 防死循环五层机制

```
第 1 层 · Prompt 层:         "单次诊断控制在 3 步以内"
第 2 层 · Harness 快路径:    剩余步骤 ≥ 阈值 且 上一步成功 → 跳过 LLM
第 3 层 · 硬性步数上限:      iteration >= max_steps → 强制出报告
第 4 层 · 重复检测:          连续 3 步 fingerprint 相同 → 强制收敛
第 5 层 · LangGraph 限制:    recursion_limit = max_steps * 3 + 5
```

## 4. Skill 系统

### 4.1 Skill 的定位

```
Tool (工具)          = 螺丝刀、扳手 (单个能力)
Skill (技能/剧本)    = 修车的标准流程 (用什么工具、按什么顺序、输出什么)

search_knowledge_base    ─┐
get_local_cpu_memory     ─┤ 这些都是 Tool
ping_host                ─┤
docker_ps                ─┘

host_resource_diagnosis  ─── 这是一个 Skill
  ├─ "先拍快照 (get_local_system_overview)"
  ├─ "再按 CPU/内存/磁盘分支 (get_local_cpu_memory / get_local_disk_usage)"
  ├─ "找高占用进程 (list_top_processes)"
  └─ "输出格式: 现状快照 + 问题判断 + 根因 + 止损建议"
```

### 4.2 SKILL.md 双层结构

```
┌──────────────────────────────────────────────┐
│  YAML Frontmatter (给代码读的)                 │
│  ─────────────────────────────                │
│  name: host_resource_diagnosis   ← 唯一 ID    │
│  display_name: 主机资源诊断       ← 给人看     │
│  description: ...                 ← 给Router看 │
│  triggers: [cpu高, 内存高, ...]  ← 触发关键词  │
│  allowed_tools: [get_local_...]  ← ★工具白名单 │
│  risk_level: low                  ← 风险等级   │
│  context: inline                  ← 执行模式   │
├──────────────────────────────────────────────┤
│  Markdown Body (给 LLM 读的)                   │
│  ─────────────────────────────                │
│  # 主机资源诊断 Playbook                       │
│  ## Phase 1: 先拍快照                          │
│  1. 调 get_local_system_overview              │
│  ## Phase 2-A: CPU 分支                       │
│  1. 调 get_local_cpu_memory                   │
│  2. 调 list_top_processes(sort_by=cpu)        │
│  ## Phase 3: 输出报告                          │
└──────────────────────────────────────────────┘
```

### 4.3 启动加载 → 全局单例

```
应用启动 (main.py lifespan)
  │
  ▼
get_skill_registry()  ← @lru_cache(maxsize=1) 进程级单例
  │
  ▼
_scan_definitions(Path("app/skills/definitions"))
  │
  ├─ 扫描 */SKILL.md
  ├─ load_skill_from_file() → 正则分离 YAML frontmatter + Markdown body
  │    ├─ YAML 解析失败 → SkillLoadError → 跳过 (不影响启动)
  │    └─ Pydantic 校验失败 → SkillLoadError → 跳过
  │
  └─ 返回 SkillRegistry({name: Skill, ...})
       ├─ .names() → ["host_resource_diagnosis", "network_diagnosis", "container_diagnosis", "generic_oncall"]
       ├─ .get(name) → Skill | None
       ├─ .get_or_generic(name) → Skill (找不到就回退 generic_oncall)
       └─ .to_router_menu() → Markdown 菜单 (给 Router LLM 看)
```

### 4.4 Skill 如何影响三个核心节点

**① 影响 SkillRouter — 选择哪个 Skill**

```python
# skill_router.py
registry = get_skill_registry()
menu = registry.to_router_menu()  # 拼成 Markdown 菜单

# LLM 被要求从菜单中选一个
choice = await ainvoke_structured(llm, SkillChoice, messages)
# 返回: {is_oncall: true, skill_name: "host_resource_diagnosis", confidence: 0.95}
```

**② 影响 Planner — Playbook 注入 Prompt**

```python
# planner.py
skill = registry.get_or_generic(state["selected_skill"])
messages = harness.build_planner_messages(
    user_input=user_input,
    skill_playbook=skill.playbook,  # ← 整个 Markdown body 注入 prompt
)
# LLM 拿到: "你是资深SRE..." + 用户输入 + Playbook 全文
# 所以 Planner 不是凭空想步骤，而是把 Playbook 翻译成具体操作
```

**③ 影响 Executor — 工具白名单**

### 5.3 Step 1: 向量粗排 (Bi-Encoder)

```
"CPU 100% 怎么处理"
    │
    ▼
OpenAIEmbeddings(model="text-embedding-v4", dimensions=1024)
    │
    ▼
Milvus.similarity_search(query, k=20)
    │
    ▼
HNSW 索引 ANN 搜索 (metric=COSINE, ef=32)
    │
    ▼
返回 top-20 个 Document
```

### 5.4 Step 2: Hybrid 融合 (BM25 + Vector → RRF)

BM25 补充向量检索的盲区：

```
向量检索 (COSINE):                          BM25 (关键词):
  擅长: 语义相近的概念                      擅长: 错误码、组件名、英文术语
  盲区: "ERR_CONN_REFUSED" 语义弱           盲区: 中文长句的语义理解
```

RRF 融合公式：

```
RRF score(d) = Σ weight_i / (60 + rank_i(d))

k=60 是 TREC 经典默认值，防止头部文档得分过高
默认 BM25 权重 = 0.4, Vector 权重 = 0.6
```

### 5.5 Step 3: Reranker 精排 (Cross-Encoder)

```
Bi-Encoder (粗排):                      Cross-Encoder (精排):
  query ──► [向量] ──┐                   (query, doc1) ──► [gte-rerank-v2] ──► 0.87
                      ├─ cosine          (query, doc2) ──► [gte-rerank-v2] ──► 0.62
  doc1 ──► [向量] ──┘                   (query, doc3) ──► [gte-rerank-v2] ──► 0.91
                      一次 ANN 搜索           每对都要跑一次模型
                      延迟: ~10ms             延迟: ~300ms/20个候选
```

Reranker 的输入就是 Step 1+2 的 20 个候选，不是从头搜索。只对这 20 个重新打分排序取 top-3。

### 5.6 三步分工：成本模型

```
Bi-Encoder (Step 1+2):           Cross-Encoder (Step 3):         LLM (最终消费):
4080 chunks → top-20             20 candidates → top-3           3 chunks → 回答
     ~10ms                           ~300ms                        ~2-5秒
     $0.0001                         $0.001                        $0.01
```

### 5.7 降级策略

```
Step 1 向量检索失败  → 返回空 [] → 工具返回"知识库未命中"
Step 2 BM25 不可用   → 跳过 RRF，直接返回向量结果
Step 2 BM25 无结果   → 跳过融合，返回纯向量结果
Step 3 Reranker 超时 → 降级到粗排 top-3
Step 3 API Key 缺失  → 直接降级
任一步抛异常         → 捕获后自动降级到上一层结果
```

### 6.1 MCP 协议本质

把"函数调用"变成"HTTP 服务"：

```

                                         └──────────┘              │ (独立进程)   │
```

## 8. 前端 SSE 流式

### 8.1 三层架构

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 3: 前端 (app.js)                                          │
│  ReadableStream → 逐行解析 SSE → JSON.parse → 增量更新 DOM       │
│  consumeSSE() → handleAiopsEvent() → 更新步骤卡片/监控面板/报告   │
└────────────────────────────┬────────────────────────────────────┘
                             │ HTTP SSE (text/event-stream)
                             │
┌────────────────────────────▼────────────────────────────────────┐
│  Layer 2: FastAPI 中转 (aiops_service.py)                        │
│  EventSourceResponse → async generator → yield SSE events       │
│  合并两个源: graph.astream 节点事件 + token_queue 的 token 事件   │
└────────────────────────────┬────────────────────────────────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
        ▼                    ▼                    ▼
┌───────────────┐  ┌──────────────────┐  ┌──────────────────┐
│ Layer 1:      │  │ stream_sink.py   │  │ tool_runner.py   │
│ graph.astream │  │ ContextVar +     │  │ emit(token)  →   │
│ → 节点事件    │  │ asyncio.Queue    │  │ stream_sink      │
└───────────────┘  └──────────────────┘  └──────────────────┘
```

### 8.2 Layer 1: 事件产生的核心机制

LangGraph 的 `graph.astream()` 只产出节点级事件。`stream_sink.py` 用 ContextVar + asyncio.Queue 把 tool_runner 内部的 LLM token 旁路出去：

```python
# stream_sink.py
_sink_var: ContextVar[Optional[asyncio.Queue]] = ContextVar("executor_stream_sink")

def set_sink(queue):    _sink_var.set(queue)

async def emit(event):
    q = _sink_var.get()
    if q: q.put_nowait(event)   # 推到队列
```

ContextVar 跨 Task 传递：

```
aiops_service 主协程                      tool_runner (子 Task)
─────────────────────                    ─────────────────────
queue = asyncio.Queue()                         │
set_sink(queue)    ──── ContextVar ──────────►  │
create_task(_graph_runner) ── 启动子Task ──►  llm.astream()
                                                   │
while True:                                   每个 token:
  item = await queue.get()         ◄───────  emit({"type":"step_token",
  yield SSE event                                 "content": chunk})
```

### 8.3 Layer 2: 两路事件合并

```python
# aiops_service.py:92-164
async def stream_diagnose(query):
    token_queue = asyncio.Queue(maxsize=2048)
    set_sink(token_queue)

    async def _graph_runner():
        async for event in graph.astream(...):
            await token_queue.put({"__node__": event})  # 节点事件
        await token_queue.put(done_sentinel)

    runner_task = asyncio.create_task(_graph_runner())

    while True:
        item = await token_queue.get()
        if item is done_sentinel: break

        if "__node__" in item:           # ← 来自 graph.astream
            for node_name, output in item["__node__"].items():
                async for sse in _convert_node_event(node_name, output):
                    yield event
        else:                             # ← 来自 tool_runner 的 emit()
            yield event
```

### 8.4 Layer 3: 前端 SSE 消费

```javascript
// app.js:870-915 — consumeSSE()
async function consumeSSE(response, onEvent) {
    const reader = response.body.getReader();   // ReadableStream API
    const decoder = new TextDecoder("utf-8");
    let buffer = "";

    while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        buffer += decoder.decode(value, { stream: true });

        // 按 \n\n 切出完整的 SSE event block
        let parts = buffer.split(/\r?\n\r?\n|\n\n/);
        buffer = parts.pop();  // 最后一段可能不完整，留着
        for (const block of parts) parseBlock(block);
    }

    function parseBlock(block) {
        for (const line of block.split(/\r?\n/)) {
            if (line.startsWith("data:")) {
                onEvent(JSON.parse(line.slice(5).trim()));
            }
        }
    }
}
```

## 公司项目改造路径

基于这个项目框架，你的公司项目只需要做：

1. **新增 CMDB MCP Server** — `mcp_servers/cmdb_server.py`, 提供 `query_cmdb` 工具
2. **导入公司运维手册** — 写 Markdown SOP 文档 → `scripts/ingest_kb_corpus.py` 导入 Milvus
3. **定义公司 Skill** — `app/skills/definitions/` 下新建 Skill, 定义告警处理流程
4. **改造告警接入** — 复用 `POST /api/v1/webhook/alertmanager` → 解析 JSON 告警 → 提取关键字段 → 触发诊断
5. **定制报告模板** — 修改 AgentHarness 的 `_REPORT_SYSTEM_PROMPT`, 加入风险等级输出格式

核心链路不变: 告警 → SkillRouter(匹配告警类型) → Planner(基于 SOP 制定步骤) → Executor(调 CMDB + RAG) → Replanner(风险评估) → 最终报告。
