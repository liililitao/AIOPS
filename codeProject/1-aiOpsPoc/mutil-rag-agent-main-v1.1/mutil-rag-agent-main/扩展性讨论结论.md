### 优先级 4: 告警预处理规则（半日可做完）

**改动：** 3 个文件

| 文件 | 作用 |
|------|------|
| `app/runtime/alert_rules.py` (新) | 规则引擎：条件匹配 + 动作执行 |
| `app/runtime/alert_rules.yaml` (新) | 规则配置文件 |
| `app/api/v1/splunk.py` | 在 `_run_diagnosis()` 前插入 `apply_rules(payload)` |

**规则配置（YAML）：**
```yaml
# app/runtime/alert_rules.yaml
rules:
  - name: 测试环境跳过
    when:
      alert_type: any
      host_ip_in_env: test
    action:
      skip: true
      set: {risk_level: 1, priority: "低", report: "测试环境告警，自动跳过诊断"}

  - name: 核心支付网关自动升级
    when:
      host_ip_in: ["10.0.1.101", "10.0.1.102"]
      severity_in: ["high", "critical"]
    action:
      escalate: true
      set: {min_risk_level: 4, priority: "紧急"}

  - name: 告警风暴去重
    when:
      same_ip_in: "5min"
      same_type_in: "5min"
      count_gte: 5
    action:
      deduplicate: true
      merge_into: 1
```

**规则引擎核心逻辑：**
```python
# app/runtime/alert_rules.py
def apply_rules(payload: dict) -> RuleResult:
    for rule in load_rules():
        if matches(rule.when, payload) and check_window(rule, payload):
            return execute(rule.action, payload)
    return RuleResult(passthrough=True)  # 未命中任何规则 → 走 Agent
```

**模仿对象：** `agent_harness.py:evaluate_replanner_pre_llm()` — 同样的"先做代码级判断，再决定是否调 LLM"模式。

## 四、技术栈迁移：从 PoC 到公司生产环境

> 公司要求的 6 项技术栈，按"对 Agent 代码的影响程度"分级讲解。

### 4.0 迁移对照总表

```
                    当前 PoC                        公司目标
                    ────────                       ────────
向量数据库:          Milvus                    →    Milvus（不变）
全文搜索:           内存 BM25 (rank_bm25)       →    OpenSearch（改动 300 行）
关系数据库:          Python dict (Mock CMDB)    →    PostgreSQL + Flink+Kafka（改动 100 行）
AI 大脑:            DashScope (qwen3.6-plus)  →    公司内部 AI API（0 行代码）

```

### 4.1 Milvus — 不动

**影响：零。** 已经在用。公司要求也是 Milvus，完全匹配。

---

### 4.2 OpenSearch 替换内存 BM25

**为什么换：** 当前 BM25 有两个硬伤——进程重启丢失索引、上限 16384 条 chunk。OpenSearch 是持久化的全文搜索引擎，天然支持分布式、无条数上限、断电不丢。

**改动范围：**

| 文件 | 改动 | 行数 |
|------|------|------|
| `app/core/hybrid_retriever.py` | 删除 `_BM25Index` 类（~90行），新增 `OpenSearchClient`（~80行） | ~170 |
| `app/core/opensearch_client.py` ★新 | OpenSearch 连接管理 + 索引创建 + 检索 API | ~80 |
| `scripts/ingest_kb_corpus.py` | 入库时双写：embedding→Milvus + 文本→OpenSearch | ~30 |
| `app/services/document_service.py` | upload/delete 时间步刷新 OpenSearch 索引 | ~20 |
| `docker-compose.yml` | 加 `opensearch-node1` + `opensearch-dashboards` 服务 | ~20 |
| `.env` | 加 `OPENSEARCH_HOST`、`OPENSEARCH_PORT` | ~3 |

**架构不变：** Hybrid Search 的三步流水线完全不动：
```
之前: query → Vector(Milvus) + BM25(内存) → RRF融合 → Reranker → LLM
之后: query → Vector(Milvus) + BM25(OpenSearch) → RRF融合 → Reranker → LLM
                                                   ↑
                                        只换了这一层的实现
```

---

### 4.3 CMDB：PostgreSQL + Flink CDC + Kafka

这组技术栈最容易被误解——它不是三件事，**而是一条数据同步链路**。拆开来讲。

#### 4.3.1 为什么需要这条链路

**场景：** CMDB 部署在公司云服务器上的 PostgreSQL 里。Agent 每次收到告警都要查 CMDB 获取设备信息。

```
告警风暴时的问题:
  100 条告警 × 每条诊断都查 CMDB
  = 100 次 PostgreSQL 查询
  + PostgreSQL 同时还在被其他系统频繁更新

→ PostgreSQL 可能成为瓶颈
→ 解决方案: 不直接查 PostgreSQL，查它的"影子副本"
```

#### 4.3.2 三个组件各干什么

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     公司云服务器                                          │
│                                                                         │
│  ┌──────────────┐                                                       │
│  │ PostgreSQL   │  ← CMDB 主库                                          │
│  │ (CMDB 数据)  │     存放: 设备表、应用表、业务线表、负责人表             │
│  │              │     运维人员在这里增删改 CMDB 数据                       │
│  └──────┬───────┘                                                       │
│         │ 写操作产生 WAL 日志 (Write-Ahead Log)                          │
│         │ INSERT / UPDATE / DELETE 都被记录                              │
│         ▼                                                               │
│  ┌──────────────┐                                                       │
│  │ Flink CDC    │  ← Change Data Capture 连接器                         │
│  │              │     读 PostgreSQL 的 WAL 日志                          │
│  │              │     把每一条 INSERT/UPDATE/DELETE 转成事件              │
│  │              │     "devices 表的主键=5 的记录, app_name 从 A 变成 B"   │
│  └──────┬───────┘                                                       │
│         │ 变更事件流                                                      │
│         ▼                                                               │
│  ┌──────────────┐                                                       │
│  │    Kafka     │  ← 消息队列 (高吞吐、持久化)                             │
│  │              │     Topic: cmdb.devices.change                        │
│  │              │     事件堆积在 Kafka 里，消费者随时来取                   │
│  │              │     像水库——上游 PostgreSQL 下暴雨（大量更新），            │
│  │              │     下游可以慢慢消费，不会被冲垮                          │
│  └──────┬───────┘                                                       │
│         │                                                               │
└─────────┼───────────────────────────────────────────────────────────────┘
          │
          │ 消费者从 Kafka 拉事件
          ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                     本地 / Agent 侧                                      │
│                                                                         │
│  ┌──────────────┐    ┌──────────────────┐                               │
│  │    Flink     │    │   OpenSearch     │                               │
│  │ (流处理引擎)  │    │   (全文搜索)      │                               │
│  │              │    │                  │                               │
│  │ 从 Kafka 消费 │───►│ 把 CMDB 数据同步  │                               │
│  │ 加工+清洗     │    │ 到 OpenSearch 中 │                               │
│  │ 写入下游      │    │                  │                               │
│  └──────────────┘    └────────┬─────────┘                               │
│                               │                                         │
│                               │ Agent 查 CMDB 时，从 OpenSearch 读       │
│                               │ (不走 PostgreSQL，毫秒级)                 │
│                               ▼                                         │
│                      ┌──────────────────┐                               │
│                      │  query_cmdb()    │                               │
│                      │  app/tools/      │                               │
│                      │  cmdb_tool.py    │                               │
│                      │                  │                               │
│                      │  优先查 OpenSearch│                              │
│                      │  (已同步CMDB快照) │                               │
│                      └──────────────────┘                               │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 4.3.3 对你的类比理解

你之前说"CPU cache 的感觉"——非常准确：

```
CPU 体系:                          CMDB 查询体系:
─────────                          ─────────────
CPU 直接读内存 → 慢                Agent 直接打 PostgreSQL → 慢
CPU 先读 L1 cache → 快             Agent 先读 OpenSearch → 快
Cache 由硬件自动同步               OpenSearch 由 Flink+Kafka 自动同步
程序不感知 cache 存在               Agent 代码不感知 Kafka 存在
```

#### 4.3.4 Agent 代码改动

**对 Agent 来说几乎零改动：**

```python
# app/tools/cmdb_tool.py — 唯一需要改的文件

# 当前 (PoC):
_MOCK_CMDB = {"10.0.1.101": {...}}  # Python 字典

# 改为:
async def query_cmdb(ip: str = "") -> str:
    # 从 OpenSearch 查 CMDB 快照（已被 Flink+Kafka 同步）
    result = await opensearch_client.search(
        index="cmdb_devices",
        query={"term": {"ip": ip}}
    )
    return format_cmdb_result(result)
```

**Agent 不知道也不关心：**
- 数据是从 PostgreSQL → Flink CDC → Kafka → Flink → OpenSearch 这条链路来的
- 它只知道问 OpenSearch："这个 IP 的设备信息是什么"
- 同步链路由 Flink 团队维护，Agent 代码不用管

#### 4.3.5 改动清单

| 文件 | 改动 | 说明 |
|------|------|------|
| `app/tools/cmdb_tool.py` | `_MOCK_CMDB` → `opensearch_client.search()` | ~30 行 |
| `app/core/opensearch_client.py` | cmdb_tool 也要用同一个 OpenSearch 客户端 | 复用上面 4.2 建的 |

**不需要改的文件：** `app/api/v1/splunk.py`、`app/agents/executor.py`、`app/skills/definitions/*/SKILL.md`——对外接口完全不变。

**不需要 Agent 团队做的事：** 部署 Flink CDC 连接器、建 Kafka Topic、写 Flink 流处理作业——这些是基础设施/数据平台团队的事。Agent 只负责消费结果。

### 4.4 公司内部 AI API — 改 3 个环境变量

**为什么几乎不改：** 项目用的是 LangChain 的 `ChatOpenAI`（OpenAI 兼容协议）。市面上主流的模型 API（DeepSeek、Qwen、GLM、以及大部分公司自建 API）都兼容这个协议。

**改动：**
```env
# .env — 只改 3 行
DASHSCOPE_BASE_URL=https://ai-api.company.internal/v1   # 从阿里云地址改为公司地址
DASHSCOPE_API_KEY=company-internal-key                   # 从阿里云 key 改为公司 key
DASHSCOPE_CHAT_MODEL=company-llm-model                   # 从 qwen3.6-plus 改为公司模型名
```

**如果公司 API 不支持 structured output（Pydantic 强制输出）：**
- Planner 会触发 fallback → 用 fallback_plan（已在代码里，第 2 步见过）
- Replanner 会触发 fallback → `_force_summary()`
- **不影响系统运行，只是诊断质量略降**（Fallback 是泛化步骤而非定制步骤）
- 解决方案：在 Harness 的 `build_planner_messages()` 里加更强的格式约束（一两行 prompt 改动能解决）

## 六、关键设计原则（此次讨论的共识）

### 功能扩展原则
1. **Skill 版本化用"运维手动切 + 重启"** — 10 种告警类型，灰度不划算
2. **知识库"覆盖上传"即"改"** — 几百篇文档规模，不需要增量更新
3. **预处理规则在 Agent 之前** — 模仿 Harness 的 pre-LLM 检查模式，秒级处理简单告警，贵的 Agent 留给复杂告警
4. **测试环境通过模型分层区分** — 利用已有的 Harness 模型分层能力，不新增代码
5. **所有扩展不改变 LangGraph 编排核心** — SkillRouter/Planner/Executor/Replanner 的图结构保持不变

### 技术栈迁移原则
6. **OpenSearch 只替换 BM25 那一路** — Hybrid Search 的 RRF 融合、Reranker 精排、向量检索全部不动
7. **Flink+Kafka 是基础设施，Agent 不感知** — 数据同步链路由基础架构团队维护。Agent 只从 OpenSearch 读 CMDB 快照，不关心数据从哪来的
8. **所有外部依赖对 Agent 暴露统一接口** — 无论 Mock dict / PostgreSQL / OpenSearch，Agent 看到的永远是一个 `query_cmdb(ip) → Markdown` 的函数，实现可随时替换
9. **环境差异通过 .env 控制，不 new 分支** — 生产/测试的模型、CMDB 地址、AI API 地址全部 .env 区分
